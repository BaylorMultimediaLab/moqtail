## Findings

**[Major] Seam PTS and gap fields come from the landing object even when it is dropped as pre-keyframe** — player.ts:891-894, 913-915, 926-928, 931, 935. `new_start_pts_ms`, `media_seam_gap_ms`, `seam_ahead_of_playhead_ms` and `postSwitchSeamPTS_ms` are taken from the landing object; if `landed_on_keyframe` is false, that object is discarded at 1026-1039 and the first appended target frame is the next sync sample (up to one GOP later). Native SWITCH lands on object 1 by design, so for that arm `media_seam_gap_ms` reads ~0/one frame while the real buffered hole is ~1 GOP; the struct doc (104-106) promises "first appended target frame's PTS". The seam metrics then disagree between mechanisms for reasons unrelated to the mechanism. Fix: emit (or append to) SWITCH_APPLIED and set `postSwitchSeamPTS_ms` from the first object that passes the keyframe gate; keep `SWITCH_FIRST_OBJECT` for the landing object.

**[Major] SWITCH_FIRST_FRAME fires on a source frame when the seam lands at or behind the playhead** — player.ts:1504. The test is only `mediaMs >= seam - frame/2`. A pr1378 playhead-floor switch (or a native switch with negative `media_seam_gap_ms`) lands target frames behind or under the playhead, so the next presented _source_ frame satisfies the test: t5 ≈ t4, `playback_position_jump_ms` = 0, `seam_buffer_hole_ms` = 0, and the viewer has not seen the new rung. This biases visibility delay in favour of exactly the mechanism that re-fetches from the playhead. Fix: track the target's appended PTS range per switch (`seam .. lastAppendedEndPTS_ms`) and fire only when `seam <= mediaMs <= targetAppendFront` and the frame was presented after that PTS was appended; log `seam_behind_playhead: true` when `seam_ahead_of_playhead_ms < 0`.

**[Major] THROUGHPUT_SAMPLE timestamps are taken in the serialised append path, not at arrival** — player.ts:1122 after `await waitForBufferUpdate` at 1063; goodput.ts:91, 198. WritableStream delivers the next chunk only after the previous `write()` resolves, so `t_N - t_1` includes N-1 `appendBuffer`+`updateend` round trips. A cached group bursting at line rate (time-shifted clients, cache replay) is capped by MSE append rate, while a live-forwarded group is paced by the publisher; the estimate therefore differs by client type independent of the link. Fix: stamp receive time upstream of the pipe (a TransformStream on `struct.source` that attaches `Date.now()` to each object) and feed that into `recordObject`.

**[Major] Stale-track bytes are invisible to the throughput estimate** — player.ts:790-807, 1122, 1608/1688. DROP_STALE objects return before `recordObject`, so a group sample and the probe's `v_bytes` count only appended bytes while the link was also carrying the old track's backlog (`seam_dropped_source_frames`). The post-switch sample under-reads capacity by the discarded share, which is precisely what differs between the three mechanisms, nudging the ABR toward down-switches after a native landing. Fix: record discarded bytes in the tracker (separate counter) and either include them in the group sample or expose `discarded_bytes` on THROUGHPUT_SAMPLE so the analyzer can correct.

**[Major] `buffer_s` counts across holes** — player.ts:1307-1310: `buffered.end(last) - currentTime`. The ABR (`AbrController.ts:223,250,279`) and `playable_data_ahead` (analyze.py:135-140) consume it. A 1-GOP hole left by a native landing, or old source data ahead of a pr1378 playhead-floor fill, is reported as playable buffer. dash.js uses the range containing the playhead. Fix: add `buffer_contig_s` (end of the range containing the playhead minus playhead) and feed the ABR from it; keep the old value as `buffer_total_s`.

**[Major] SAMPLE.track / bitrate_kbps switch at landing (t4), not at visibility (t5)** — player.ts:848 sets `struct.trackName` at SWITCH_FIRST_OBJECT; `getMetrics().activeTrack` (1351) and MetricsCollector (62, 98) follow it. "Played rung", rung share and `reaction`/`recovery` (analyze.py) are therefore computed from the _receiving_ rung. For a time-shifted client with a multi-second buffer the viewer sees the old rung for `seam_ahead_of_playhead_ms` longer, and that distance differs by client type and mechanism. Fix: keep a list of `(seamPTS, track)` and emit `presented_track` resolved from `playheadMs` in SAMPLE; also set `STALL_START.track` from it.

**[Major] The wedge watchdog overrides RANGE_JUMP_DEFERRED after 1 s for gaps < 1.5 s** — player.ts:557-576 vs buffer.ts:65-78, 131. The deferral is documented as bounded by 3 s of no append-front progress (schema l.91, 234-238), but when the playhead parks at the range end the wedge branch seeks across any gap < 1.5 s after two frozen ticks (`frozenSince >= 2`). The deferral exists to protect the time shift during a pr1378 fill, so its real bound is 1 s for that case. Fix: have the wedge branch consult the same `gapFillProbe` (skip while `shouldDeferRangeJump` is true and front moved < 3 s ago), or document the 1 s effective bound.

**[Minor] Live-edge rate controller cannot settle on 1 s group bursts** — buffer.ts:22-23, 26, 451-485. Target 0.6 s ± 0.1 s against a buffered end that advances in GOP-sized steps means `currentLatency` sweeps ~1 s each second; the controller toggles catch-up/catch-down every group (PLAYBACK_RATE spam) and the minimum margin before the next burst is ~0.1 s, so jitter > 100 ms produces `waiting` stalls on every arm. Mechanism-neutral, but live-edge stall counts then measure player tuning. Consider a dead band ≥ one GOP, or a target expressed as "buffered end minus 1 GOP".

**[Minor] Init-apply failure path skips the keyframe gate and all seam records** — player.ts:865-880, 1003-1024. After `SWITCH_INIT_RECOVERED`, `awaitKeyframe` and `postSwitchSeamPTS_ms` are never set, so the next (possibly non-sync) frame is appended and the switch produces SWITCH_FIRST_OBJECT without SWITCH_APPLIED/SWITCH_FIRST_FRAME. Fix: run the landing block (seam/keyframe) after a successful retry.

**[Minor] `lastAppendedEndPTS_ms`/TimeMap updated before the append succeeds** — player.ts:1045-1052 vs 1086-1096. On `append-exhausted` the append front and group boundary advance for a frame that is not in the buffer; `getAppendFrontMs` then misleads the range-jump deferral. Move the update after the retry loop.

**[Minor] Throughput sample attribution** — player.ts:1127-1129: `track: struct.trackName` is the current track at finalisation but the sample is for the previous group, which may belong to the previous track; a mid-group landing also merges source and target bytes of the same group id (goodput.ts:95). Record the track per group in the tracker.

**[Minor] rAF fallback for rVFC is not flagged** — player.ts:1577-1583. In the fallback `playback_position_jump_ms` is `currentTime` delta minus one frame (systematically negative at 60 Hz polling) and `viewer_pause_ms` is clamped to 0. Add `source: 'rvfc'|'raf'` to SWITCH_FIRST_FRAME and STARTUP.

**[Minor] RUN_META emitted before the effective ABR settings exist** — app.tsx:497-518 vs 545-574. `__abrSettingsOverride` is merged after RUN_META; no runner currently injects it (grep: none in `experiments/`, `tests/`), so latent. Also `startPlayback` (639-645) creates a second Player without `logObjects` and without RUN_META. Emit RUN_META after the merge, or drop the override path.

## Findings

**[Critical] LatencyTrendRule's sensitivity is client-type dependent by roughly shift/e2e** — `player.ts:1230` (`latency = Date.now() − prft.captureMs`), `latencyTracker.ts:58-67`, `LatencyTrendRule.ts:54`. The signal is capture-to-receipt latency, so a 10 s time-shifted client's baseline is ~10.1 s and a live-edge client's ~0.1–0.4 s. The 1.2 ratio trigger therefore needs a ~2 s rise on the time-shifted client (never happens) and a ~20–80 ms rise on the live-edge one (every queue wobble). The rule is a STRONG one-rung down-switch and is effectively "on" for one client type and "off" for the other; `latencyResetOnLanding` fixes the seam burst only. It also is not relay→client latency (that is only in the analyzer), so a mechanism that starts the target at an older cursor shifts the baseline. Fix: compute the trend on `latency − targetShiftMs` (or on relay→client delay if the relay stamps it), or use an absolute-delta threshold, or drop the rule from `grid`.

**[Major] Buffer rules convert a mechanism's seam hole into a 60 s ladder cap** — `BufferDrainRateRule.ts:90-113, 129`, `InsufficientBufferRule.ts:61, 73`, `SwitchHistoryRule.ts:33-37, 63-76`. A one-group delivery gap after a native switch reads as drain ≈ 1 s/s ⇒ `linkBps = bitrate × (1.05 − 1.0) ≈ 0` ⇒ STRONG vote for rung 0; the resulting `auto-downgrade` is then a "drop" against the rung, and with veto it caps the ladder below that rung for 60 s. The seam cost is therefore paid twice (the stall, then a minute at low quality) and more on mechanisms with bigger holes. The doc (9.3, 9.5) calls this "the mechanism's cost and stays", but the history penalty is the controller's, not the mechanism's. Fix: don't count drops that occur within ~2 groups of a landing toward SwitchHistory, or hold buffer-derived down-switches for one group after landing (symmetrically for all mechanisms), and report the seam stall as the mechanism's cost.

**[Major] Phantom switches enter the history** — `AbrController.ts:505-538`: `#recordHistory`, `ABR_DECISION`, up-guard arm and `#tracksize` all happen before `switchTrack`, and nothing rolls back when the player refuses (`player.ts:1764` missing catalog data, `:1805` `SWITCH_SKIPPED`, `:1847/:1884` `SWITCH_ERROR`), each of which calls `onTrackSwitched(oldTrack)` and releases the guard. SwitchHistoryRule's veto counts these as drops/noDrops on rungs the client never visited; the analyzer's switch count from `ABR_DECISION` also inflates. Fix: move history recording to the `onTrackSwitched` callback and only when `trackName === target`.

**[Major] ProbeRule inverts its own intent and the 64 KB cap makes it inert above ~2 Mbps** — `ProbeRule.ts:66-70`, `player.ts:1611-1624, 1683, 1697`. The probe votes only `i+1` at DEFAULT and abstains when it sees no headroom; via min-index this means a strong probe _limits_ ThroughputRule to one rung per switch while a weak probe lets its multi-rung jump through unvetoed. Also `bps = (v+p)·8/(tEnd−tStart)` where the window includes the fixed 250 ms idle wait (`:1623`); with p = 64 KB and 1.2 Mbps video, BWE tops out near 2.7 Mbps, so `0.8·BWE ≥ 4 Mbps` can never certify 1080p; the top of the ladder is climbed by ThroughputRule alone. The `dtMs` returned for the min-duration filter (`:1697`) is correct, only `bps` is wrong. Fix: `bps = p·8/(lastObjectAt − firstObjectAt)`, and make ProbeRule return `activeTrackIndex` when `0.8·BWE < next` (a veto), or remove it.

**[Major] No hysteresis or dwell time in `grid`** — `AbrRulesCollection.ts:122-156`, `AbrController.ts:291-294, 331`. The only damping is the landing guard (~1 group) and the veto, which needs `drops+noDrops ≥ 8` events on one rung inside 60 s (`SwitchHistoryRule.ts:50-54`), i.e. it engages only during a storm. Between Throughput (0.9·SWMA up/down) and the buffer rules an A→B→A at 1 switch/s is permitted (doc 9.7 reports ~6 reversals/min live-edge). Fix: minimum dwell before an up-switch (N completed groups on the current rung; the existing `upGuardSamples` is exactly this but was rejected because of finding 2) or an up-switch margin (e.g. `0.9·SWMA ≥ bitrate_{i+1}` _and_ `≥ 1.1·bitrate_i`).

**[Major] InsufficientBufferRule is a second throughput rule with a client-type-dependent safety factor** — `InsufficientBufferRule.ts:28, 61`; `types.ts:177` `stableBufferTime = 18`; `buffer.ts:22` live-edge target 0.6 s. Buffer never reaches 18 s on either client, so the rule is always active; its cap is `0.7·SWMA·buffer` — on a live-edge client (envelope ~0.7–1.0 s) that is 0.5–0.7·SWMA and is the binding up-switch admission; on a 10 s time-shifted client it is 7·SWMA, i.e. no constraint. The live-edge client therefore climbs under a stricter rule, which is a controller policy difference between the two client types, not a property of the mechanisms. Fix: either make it emergency-only (`buffer < 0.5 s` and `== 0`) in `grid`, or make the admission explicit and equal (one safety factor for both clients) and report runway separately.

**[Minor] Guard comment contradicts behaviour** — `AbrController.ts:58-62, 291`. `totalFrames > #framesAtSwitch` is satisfied by any presented frame, including old-track frames still buffered; on a time-shifted client the guard releases one tick after landing, not when a new-track frame is decoded. The behaviour is what makes landing client-neutral (doc 9.2) but the stated MSE-timeline protection does not exist.

**[Minor] `auto-emergency` is dead** — `AbrController.ts:493` requires the rule reason to contain "emergency"; no rule emits that string (`insufficient-buffer-empty`, `buffer-drain …`, `abandon-slow-delivery`, `latency trend …`). `SwitchHistoryRule.ts:33` and `SwitchReason` carry a branch that never fires.

**[Minor] Slow-start is satisfied instantly on time-shifted clients** — `AbrController.ts:93, 452`. The connect backlog (10 groups replayed in a burst) yields ~10 samples in <1 s, so `MIN_STARTUP_SAMPLES = 3` gates a live-edge client ~3 s and a time-shifted client ~0 s. Same for any "fresh samples" counter after a catch-up replay.

**[Minor] Tie-break is Map insertion order** — `AbrRulesCollection.ts:149-153` keeps the first request at equal index, so `chosen.reason` attributes ties to ThroughputRule/ProbeRule over InsufficientBuffer; attribution statistics in `ABR_TICK/ABR_DECISION` are biased by construction.

**[Minor] RUN_META records pre-override settings** — `app.tsx:510-511` logs `abrSettings`, the controller runs `effectiveAbrSettings` (`:548-582`). No caller injects `__abrSettingsOverride` in the repo today, so the grid logs are faithful; the hook is a latent fidelity gap. Hard-coded constants (tick, 3 s/5 s, 3 samples, probe 2000/500/5000 ms, horizon 2 s, SWMA 5, latency window 100, envelope 1250 ms, live-edge target 0.6 s, rate nudge 1.05) are not in RUN_META; they are pinned only by `identity.git_sha`.

## Ambiguities and inconsistencies

- `segmentDurationS: 1` and `isLowLatency: false` are hard-coded (`AbrController.ts:388-389`) while the GOP comes from the catalog; `bufferEnvelopeMs = 1250` also assumes 1 s groups.
- `segmentIgnoreCount` and `minThroughputSamplesThreshold` count ticks, not groups (`InsufficientBufferRule.ts:20-23`, `AbandonRequestsRule.ts:23`); the doc notes this (section 8) but the parameter names say otherwise.
- `activeTrackIndex` flips at landing (`player.ts:848` → `getMetrics` `:1351`), so rules reason about a rung the viewer will not see for up to a whole shift; mechanism-neutral, but client-type dependent in meaning.
- `notifySwitchVisible` fires on the first presented frame with `mediaTime ≥ seamPTS` (`player.ts:1500-1558`); if a switch lands behind the playhead (recent `SWITCH_FLOOR` work) that is the next presented frame regardless of track. Unused by `grid` (upGuardRelease only), so no controller impact, but it is not "first frame of the target".
- `initialBitrate`, `fastSwitching`, `ewma.*` are settings nobody reads (`types.ts:157-167`); `AbrRulesCollection.test.ts:58` says "all 8 rules" (there are 11).
- SwitchHistory `isUnsafe` requires `noDrops > 0` (`SwitchHistoryRule.ts:52`): the startup rung or a manually reached rung can drop forever and never be vetoed.
- Doc section 2.3 says the probe measures "(video bytes + probe bytes)/elapsed" without mentioning the 250 ms idle in the denominator; 9.9 reports "0.06 Mbps probe load" but 64 KB every 2 s is 0.26 Mbps if the cadence holds.
- `playbackRate` fed to BufferDrainRate is 0.95/1.0/1.05 from a 0.1 s dead band around a target that is 0.6 s (live-edge) or the shift (`buffer.ts:36-46, 460-478`): a hidden client-type input.

## Simplification opportunities

A minimal controller that is still fair to all mechanisms and both client types, using only mechanism-neutral inputs:

1. **ThroughputRule** on the group-burst SWMA, up and down, with an up-switch dwell of N completed groups on the current rung (reuse `upGuardSamples`, release `landed`).
2. **One emergency rule**: instantaneous buffer `== 0` or `< 0.5 s` → rung 0 / highest rung under `0.7·SWMA` (the STRONG half of InsufficientBufferRule only).
3. **SwitchHistory veto with the 60 s window**, counting only drops that occur more than ~2 groups after a landing (so seam holes are not history).
4. Keep `bufferSignal = envelope`.
   Remove or disable: BolaRule and the DYNAMIC toggle (dead below 18 s on both clients), L2A/LoLP/DroppedFrames (already off), AbandonRequestsRule (fires at SWMA < 0.55·bitrate, which ThroughputRule already covers at 0.9), BufferDrainRateRule (duplicates the emergency at the live edge, dead on time-shifted), LatencyTrendRule (client-type asymmetric, finding 1), ProbeRule and the probe track (finding 4; the SWMA already reads link rate on this relay — if the probe is kept, fix the denominator and make it a veto). ## Findings

**[Critical] SWITCH_FIRST_FRAME is joined to the wrong switch when targets repeat** — analyze.py:373 (`first(recs,"SWITCH_FIRST_FRAME", sent["ts"], to==sent.to)`). The client keeps one pending seam per stream and overwrites it on every new switch (player.ts:1495-1560), so a FIRST_FRAME record belongs to the _latest_ switch with that (from,to); the analyzer gives it to _every earlier_ unresolved switch to the same `to`. In native shift10s r3, eight distinct SWITCH_SENTs (#1,3,5,7,9,11,13,15, two different `from` tracks) all claim the one FIRST_FRAME at 79.7 s, producing visibilities of 77.6, 58.4, 40.7 ... s. Effects, per condition (analyzer vs corrected join on the record's own `from`/`to`, medians over 5 reps): native TS visibility p50 2427→2072 ms, p95 35196→7865 ms; fwd-trigger TS p50 17913→11504 ms, p95 49518→11845; pr1378 TS p50 10308→5155, p95 52433→10502; `superseded` native LE 1→11, native TS 1→15, fwd-trigger TS 13→23, pr1378 TS 10→21. viewer_pause/seam_hole/jump stats use n=50 instead of 35 (duplicate values). `ordering` in validate.py cannot catch it (t5 is always later). plot.py's seam ECDF (351) excludes "superseded" with the wrong flag, so it pools duplicates. **Fix**: join each FIRST_FRAME to the last SWITCH_SENT with ts ≤ ff.ts and matching `from` and `to` (or ff.ts − ff.switch_visibility_delay_ms ≈ sent.ts); mark all other switches superseded; use the record's own `switch_visibility_delay_ms`.

**[Critical] down-reaction / up-recovery are not comparable across conditions** — analyze.py:574-590, compare.py:42-43. `down_reaction` starts the clock at t0 regardless of where the client is: in 9 of 10 native runs the subscribed rung at t0 was already ≤ fit (2 or 3; 20 s pre-drop ≤5 % of samples above fit), hence "reactions" of 3-250 ms. Forward-trigger/pr1378 TS clients sat at rung 4 and show 6-12 s. The row therefore rewards the mechanism that never reached high quality. `up_recovery` targets the pre-drop median rung, which is 4 (1080p) for all TS runs but 2-3 for LE runs, and "never recovered" (None) is silently dropped from the median (native TS: 5/5 None → "-"). **Fix**: define reaction only when rung(t0) > fit (else N/A, report the count), or replace both by _share of time at a fitting rung during the low window_ and _share of time ≥ pre-drop rung after restore_, with the pre-drop rung reported per condition; or keep them only in the dedicated `detect_step` experiment.

**[Major] Censored metrics summarised by median-of-available** — compare.py:122-129, condition_stats 1035. **[Major] Media skipped by watchdog seeks is invisible in QoE rows** — analyze.py:313-325 only sums `wedge` gaps; range-jump `SEEK.to_ms−from_ms` is never totalled and the stall is _ended_ by the seek (player.ts closeStall on advance). ## Findings

**[Critical] `netem limit 100` counts skbs, and QUIC sends UDP-GSO super-packets on the veth** — net.py 157, 159; Cargo.lock quinn-udp 0.5.14 — quinn-udp enables `UDP_SEGMENT` GSO on Linux by default, so one skb reaching the qdisc can carry up to ~43 datagrams (~64 KB). netem's `limit` is in skbs (segmentation happens after qdisc dequeue), so the "100-packet / 150 KB" drop-tail queue is in reality 100 _bursts_, potentially several MB, and HTB (burst ≈ 2 KB) must drain each 64 KB skb as a 340 ms token debt at 1.5 Mbps, making the shaped link bursty at the sub-second scale. Nothing in `docs/`, `scripts/` or the runner disables offloads or records `tc -s qdisc`/`ethtool -k`. The "0.9 s standing delay from a 1.2 Mbps probe" noted in run_experiment.py 101-102 is consistent with a queue much deeper than 150 KB. Fix: in `NetnsBackend.setup()` run `ethtool -K <if> gso off tso off gro off tx-udp-segmentation off` on both veths (both namespaces), and dump `tc -s qdisc show dev ...` + `ethtool -k` into runner-events at each NET_CHANGE and at RUN_END so queue depth in bytes is verifiable from logs.

**[Major] Every NET_CHANGE deletes and recreates the root qdiscs on both interfaces** — net.py 133-134, called from run_experiment.py 556-564 and 610 — `tc qdisc del root` purges everything queued, including packets sitting in the netem delay line, on both the data and the ACK path. At the 60 s and 120 s steps this injects a synthetic loss burst (up to the full queue, ≈100 skbs, plus ~10 in flight) exactly at the instant whose reaction/recovery times are the headline metric; it also resets HTB/netem state. BBR's loss response and the client's probe/throughput samples right after the step are therefore contaminated. Fix: `tc class change dev veth-moqh parent 1: classid 1:10 htb rate R ceil R` and `tc qdisc change ... netem delay ...` in place; only build the tree on the first step.

**[Major] fq_codel profile changes two things, not one** — net.py 151-155 — relative to tail-drop, the AQM arm moves all 40 ms to the client→relay side (relay→client propagation 0 ms instead of 20 ms, shifting every one-way delivery/visibility metric by −20 ms) and ignores `queue_pkts` (fq_codel limit 10240). In addition, at 1.5 Mbps a 1500 B packet serialises in 8 ms > codel's 5 ms target, so codel drops/ECN-marks from a two-packet backlog; a single QUIC 5-tuple means no fair-queueing effect at all. Fix: keep netem 20 ms on the host side as a _root_ with HTB+fq_codel beneath (netem→HTB stacking works when netem is the parent), or put 20 ms on the ns side and an IFB/second netem for the other half; set `fq_codel target` ≥ 1.5× MTU-time at the lowest rate and record it; state the asymmetry in the paper if kept.

**[Major] Aborted runs are not excluded from aggregates** — run_experiment.py 692 (`if ... exit_code == 0`), analyze.py 806-812, 1079, compare.py 100 — on RUN_ABORT (process died, Ctrl-C, SystemExit) no validate.py runs, no `validation.json` is written, `read_validity` returns `valid: None`, and both aggregators test `is False`, so a truncated run with a partial client log is counted as a normal repetition. fresh-grid-v2 happened to be 30/30 valid, but the gate is open. Fix: write `validation.json {"passed": false, "failed": ["aborted"]}` in the `finally` block whenever `exit_code != 0`, or make `valid is not True` the exclusion test.

## Publisher emission model (Q8)

## Findings

**[Major] Publisher priority dominates group order across tracks at the seam** — subscription.rs:280-294, sender.rs:155, main.rs:121/582 — `priority_index=(255-sub)*256+(255-pub)` selects a 65536-wide band; group id only orders within a band. The publisher assigns `pub = N - index`, so variants sit in different bands and **the QUIC scheduler serves whichever track has the lower pub number first, regardless of group recency**. With the default ladder (1080p first → pub 4, 360p → pub 1; local `data/encoded/video/meta.json` is in this order) a down-switch's new low track wins, but an up-switch's old track (the group the client still needs) is starved; with an ascending spec ladder (`240p@150,...`) the sign flips and a down-switch's abandoned high-bitrate bytes drain before the new track. Either way the seam outcome depends on ladder order, not on the mechanism. Fix: give all video variants the same publisher priority (catalog 0), or at least document and fix the ladder order.

**[Major] `OBJECT_SENT.sent` is almost always true and `last_sent_max` advances on failed writes** — client.rs:483-510, subscription.rs:1187-1200 — `write_stream_object` returns `Ok(())` both when `write_all` fails (ClosedOrStopped) and when the stream is missing; only serialize errors produce `Err`. So `sent:false` never means "the QUIC write failed", the analyzer's cut-at-relay vs lost-after-send split is biased toward "after send", and the switch start (`old.last_sent_max+1`) can be computed from objects that were never written. Fix: propagate the write error (return `Err`) and only update `last_sent_max` on success. Also note `OBJECT_SENT` means "accepted into quinn's send buffer", not transmitted or delivered — quinn only blocks `write_all` on peer stream flow control or the 10 MB `send_window`.

**[Major] Replay/live overlap duplicates the newest group's tail and surfaces as serialize errors** — subscription.rs:454-470, 551-556, 1051-1079; subgroup_object.rs:42-45 — the live path never consults `last_received_object_location` (the comment at 551-553 describes a filter that does not exist). Objects of the newest group that arrive between sender registration and the replay's read of that group are both replayed and queued; the live copy hits the same StreamId with `previous_object_id ≥ object_id`, `object_id - id - 1` underflows (release wraps) and `put_vi` fails → `sent:false`, "Error in serializing object". Harmless on the wire, but it inflates relay-side error counts for every time-shifted subscribe that lands inside a group burst (~12% in replay mode). Fix: in the live path drop objects `<= last_received_object_location` after a replay.

**[Major] BBR initial window of 200 packets vs a 100-packet tail-drop queue** — config.rs:276-279; quinn-proto bbr/mod.rs:534,648 (`K_MAX_INITIAL_CONGESTION_WINDOW=200 × 1200 B`) — the relay's first burst to a client (cache replay of D groups, or the first group) is allowed to exceed the shaped queue by 2× before any loss signal; combined with per-group bursts (publisher emits a whole GOP in ~120 ms, relay forwards as it arrives) this produces loss at every group start while BBR is in STARTUP/PROBE_BW. Not logged except via CONN_STATS `lost_packets`/`congestion_events`. Other defaults left untouched: `stream_receive_window` 1.25 MB, `receive_window` unlimited, `send_window` 10 MB, `max_concurrent_uni_streams` 100 (toward the relay), MTU discovery on (1200→1452). Relay CLI defaults: keep-alive 3 s, idle timeout 7 s (config.rs:63-66) — a stall >7 s with lost keep-alives tears the session down. Consider logging `path.current_mtu`, cwnd at group start, and the CC name in RUN_META; consider CUBIC for an apples-to-apples comparison with the browser's CC.

**[Minor] Promotion race on SWITCH status ordering** — subscribe_handler.rs:1602-1627 vs 919-923 — alias is announced (forwarding released) before `switch_context` is set; an object queued in that window is forwarded with no gating (subscription.rs:793-796), possibly mid-group, and the old track is not demoted for it. Fix: set Next/Current before `handle_subscribe_message` (or at least before `mark_alias_announced`).

**[Minor] Old track's remaining data: FIN vs RESET depends on the client** — subscription.rs:993-1007, 1303-1309 — relay FINs; but if the client resets the old request stream (player `unsubscribe`, client.ts:1169-1173) before group g drains, the old streams are RESET and the seam gets a hole. Worth an event (`SWITCH_DEMOTED{track, last_group}`) and verifying the player's ordering.

**[Minor] Event log writes in the hot path** — events.rs:72-91 — std Mutex + `flush()` per record inside the forwarding task; with OBJECT_SENT at ~300 obj/s per client this adds synchronous disk I/O jitter to delivery timing. Buffer and flush on a timer, or emit via a channel.

**[Minor] `newest_group_id`/`oldest_group_id` use `moka::iter`, which is eventually consistent** — track_cache.rs:407-432 — the replay end can lag the real newest group by one; objects of that group that arrived before sender registration are neither replayed nor queued. Track newest/oldest in atomics on `add_object` instead.

**[Minor] Publisher replay stamps one PRFT per GOP** — replay.rs:62,88-99 — all 60 chunks of a group get the emission-time NTP; per-frame latency on the client is therefore group-granular (frame k appears k·33 ms "late"). Document or stamp per object at send time.

**[Minor] CACHE_STATS iterates the whole cache per track per second** — track_cache.rs:157-173 — `stats()` filters by `relay_track_id` needlessly (one moka instance per track) and walks every entry; cheap at 200 groups but grows with `--cache-size`.

Q8 (upstream behaviour shared by mechanisms): no PUBLISH_DONE on demotion; FIN not RESET; `last_sent_max` as the seam anchor; priority formula above; `max_subscriber_lag=0` (no shedding); serialized per-subscription forwarding task (one blocked `write_all` on any stream stalls that client's whole track, including newer groups).

## Findings

**[Critical] Subscriber priority collapses from 0 to 128 at the first switch; probe and control streams then outrank all video** — `player.ts:2105–2109` sends no parameters; `switch_delivery.rs:73–81` defaults to 128; the original SUBSCRIBE used priority 0 (`player.ts:2323`, `client.ts:1115`). With `compute_stream_priority` (`subscription.rs:327–341`): pre-switch video ≈ +2.14e9; post-switch catch-up = −1 (`switch_catchup_priority`), post-switch live ≈ −65536·(p+1) (p = publisher priority 1..5, 240p lowest); probe data stream = 0 (`subscribe_handler.rs:213`); relay-opened bidi request streams = quinn default 0. Consequences: (i) on the first switch every FIN'd byte of the old subscription (positive band) is sent before the PUBLISH itself and before any target data; (ii) from then on the 64 KB probe preempts all video (the "yield to video" comment at `subscribe_handler.rs:212` holds only before the first switch), a confound between pr1378 and any mechanism that keeps the original subscription — verify on `switch/native`. Fix: `switchTrack` passes `parameters: [new SubscriberPriority(0)]` (plus GroupOrder), as the PR's "complete parameter set" requires.

**[Major] The client discards the drained below-seam remainder** — the relay FINs streams below the seam so they deliver (`subscription.rs:930–953`), but `switchTrack` re-binds `struct.source` and aborts the pipe on SWITCH_OK (`player.ts:2147–2148`; pump `1485–1504` never reads the abandoned readable). Old-track objects still route to the old receiver (`subscriptions.get(trackAlias)`) and accumulate unread. Because the relay's drain is "written", not "acked" (`switch_delivery.rs:262–270`), on a saturated link up to k groups × R_old of link time is spent on bytes nobody consumes, ahead of the new live groups (Finding 3). This is the §10a "holes 10–20 s ahead" mechanism in a second form, and it makes the FIN-below-seam fix only partially effective. Fix: keep piping the old readable until its PUBLISH_DONE/close (or merge both readables and let the write handler order by group), then release the old receiver via `unsubscribe(oldId)` bookkeeping.

**[Major] Catch-up priority inverts play order against the source remainder** — `switch_catchup_priority` pins the FETCH stream to the top of the pub-0 band (`switch_delivery.rs:61–69`), above the old subscription's FIN'd below-seam streams (groups < G_switch, which the player needs first) whenever the old subscription is also at 128 (every switch after the first). Order on the wire after a down-switch: control/probe (0) > catch-up (−1) > old remainder (old pub band) > new live. The PR's SHOULD only concerns the target's own SUBGROUP streams; using `compute_stream_priority(sub, DEFAULT_PUBLISHER_PRIORITY, Ascending, g_switch)` satisfies it (catch-up groups < live-edge groups) while sorting correctly against the remainder. Combine with Finding 1 so old and new share a band.

**[Major] PublishBuildFailed is reported after the source is already torn down** — `terminate_source` (`subscribe_handler.rs:1901–1909`) runs before `add_subscription` (1915–1924); the failure branch (1925–1945) restores an end-group on a subscription that no longer exists (comment admits "moot") and tells the client "current untouched". The client keeps a dead `requestId`; every later SWITCH dies at the pre-validation gate (no PUBLISH) and resolves as a 6 s local Timeout forever. Fix: attach the target subscription first (forwarding is gated on `mark_alias_announced`, `publish_handler.rs:597–601`, so nothing leaks), then terminate.

**[Major] The player has no handler for the old request id's PUBLISH_DONE** — `publish_done.ts:41–51` only sets `expectedStreams`; `player.ts` never sets `onPeerPublishDone`. The conformance doc explicitly requires applications to treat a Timeout `SwitchFailure` as "source may be gone" and react to PUBLISH_DONE(SUBSCRIPTION_ENDED); the harness player does not, so the late-success path (`publish.ts:149–172`) and Finding 4 both wedge playback silently.

**[Major] Old-track groups ≥ G_switch can be appended before the reset lands, then re-delivered by the catch-up** — with the next-group floor, the relay may already have written groups ≥ G_switch (client not yet received) before the seam bound at `1874`; bytes on the wire arrive while the old pipe is still bound (SWITCH_SENT→SWITCH_OK) and are appended (`player.ts:1253–1256`), then the catch-up re-appends the same span from another representation. The next-group branch deliberately skips `remove()` (`1041–1047`). This matches the "2-frame slivers" and MEDIA_ERR_DECODE reports in `abr-controller.md`. Fix: once SWITCH_OK carries `switchingGroupId`, drop old-track objects with `group >= switchingGroupId` in the write handler (cheap, mechanism-faithful).

**[Minor] `lastGroupId` is last-arrived, not max** — `player.ts:1332` assigns; a catch-up object arriving after a live object regresses it (the root of the 9.4 s freeze the buffer-aware floor patched around). The residual: TimeMap miss or <1 complete group buffered ahead still yields a floor at/behind the playhead (`274–304, 317–349`). Use `max`.

**[Minor] Floor above the live edge is a silent 3 s wait** — `poll_select_switch_group` (`switch_delivery.rs:392–434`) emits no event while waiting; the client only sees `SWITCH_ERROR status=0xA reason="switch: NoCommonBoundary"` after T_switch, indistinguishable in status from DrainTimeout/Superseded (reason text differs; the relay's `SWITCH_FAILED.failure` names them). Emit a `SWITCH_WAIT` with the floor and both live edges.

**[Minor] No pacing anywhere** — catch-up writes the whole cached range as fast as `read_objects` yields (channel(32), `switch_delivery.rs:339–363`); the joining replay likewise; `write_stream_object` only paces under `--write-kbps-limit` (`client.rs:478–483`, default 0).

## Burst accounting at a switch (worst case, with numbers)

Setting: 1.5 Mbps link (1.5 Mbit per second of link time), 1 s GOP, time-shifted 10 s, next-group floor, delivery lag k groups (k ≤ 10 before a stall).

- A. Old subscription below-seam remainder, FIN'd, unread by the client (Finding 2): k × R_old. After the 6→1.5 drop on 1080p (4000 k) with 2–3 s controller reaction, k ≈ 2 → 8 Mbit = **5.3 s** of link, at the highest band on the first switch (Finding 1).
- B. Catch-up from cache, one burst, priority −1: (k−1) × R_new → 480p: 0.5 Mbit (0.3 s); 1080p: 4 Mbit (2.7 s).
- C. Joining replay of the live-edge head: ≤ R_new (≤ 0.1–2.7 s).
- D. New live groups queue behind A–C at the lowest priority; the controller, fed by stale throughput and `DATA_STARVED`, switches again every 0.3–1 s, each time adding a new A (previous target's remainder) and B.
  Total first switch ≈ 6 s of link on a 1.5 Mbps link before the first new-track live group can move; three switches in 2 s ≈ 10+ s of queued bytes, which is exactly the 9 s hold in §11e (there g_switch=125, live_edge=126: B+C ≈ 0.3 Mbit, so the hold was A plus the probe at priority 0, not the catch-up). `playhead` floor pathological case: B = 10 × R_new → 480p 3.3 s, 720p 8 s, 1080p **27 s** of link.
  Bounding: (1) Findings 1–3 restore play order so A never starves D; (2) pace the catch-up at ~2× R_new (token bucket on the FETCH stream) so it never exceeds what the client can play before live reaches it; (3) consume A at the client (Finding 2) so the bytes are not wasted; (4) reset old below-seam streams only when the client's floor says it already holds those groups (i.e. G_switch ≤ last group the client has fully buffered — the drain then has nothing to deliver), which is spec-compliant because nothing below G_switch is withheld.

## Source termination (Q4)

Yes: FIN'd below-seam streams keep the link ahead of the new subscription's streams (band 0 vs 128 on the first switch; same band, ascending group afterward), and the client does not read them. Resetting below-seam streams unconditionally is not compliant (the PR requires delivery below G_switch); it is compliant only when G_switch is chosen so that nothing below it is undelivered — which is what the next-group floor intends but the relay cannot verify because "delivered" is "written". The honest fix is the client consuming them.

## Time-shifted semantics (Q7)

Shift retention (~11 s) is a consequence of the floor policy plus MSE buffer retention, not of PR #1378: the PR makes the Minimum Switching Group the client's choice and says nothing about shift. A time-shifted client that wants its buffer kept should ask for 1 + highest fully buffered group (next-group); one that wants the new quality visible soon asks for the playhead group and pays B. Under next-group the catch-up is purely the delivery lag k re-requested on the new track — a side effect of a saturated link, not a mechanism feature. The harness therefore measures mechanism × floor policy; the two arms isolate the policy, but the priority collapse (Finding 1) and the unread remainder (Finding 2) currently confound pr1378 against native on both client types.

# Report 8: moqtail-ts client library (harness, with branch deltas)

## Files read

`libs/moqtail-ts/src/client/client.ts` (all 3118 lines, harness), `data_stream.ts`, `request_stream.ts`, `request/subscribe.ts`, `handler/{handler,subscribe_ok,publish,publish_done,request_error,request_update}.ts`, `types.ts`, `util/stream_reset.ts`, `model/error/stream_reset.ts`, `model/parameter/message/delay_groups.ts`, `model/control/switch.ts`, `model/data/{subgroup_header,request_id,object}.ts`; `git diff harness..switch/pr1378 -- libs/moqtail-ts` and `harness..switch/pr1674 -- libs/moqtail-ts` (full client diffs, model diffs skimmed); `apps/client-js/src/lib/player.ts` on all three branches (switchTrack, write handler, pump, probe, subscribe/unsubscribe); `apps/client-js/src/lib/goodput.ts`; relay alias assignment (`apps/relay/src/server/message_handlers/subscribe_handler.rs:914,1098`: subscriber alias = `relay_track_id`, stable per track).

## Verified correct

- One `RecvStream` per incoming uni stream, header parsed with checkpoint/restore until complete (`data_stream.ts:155-199`); subgroup-id-from-first-object resolved before routing (`:231`); peer RESET on a data stream is not escalated (`client.ts:2214-2221`, `data_stream.ts:284-297`).
- Alias route lookup waits up to 500 ms for a data stream that overtakes SUBSCRIBE_OK (`client.ts:2381-2387`); pr1674 replaces the poll with event-driven waiters (2 s) and has a regression test.
- `unsubscribe` resets the request stream with CANCELLED (`:1172`), idempotent; native `switch()` sends on the subscription's own stream and files it under the new id (`:1316-1320`).
- DELAY_GROUPS is a plain varint KVP 0x70 (`delay_groups.ts:31`), appended via `parameters` (`client.ts:1041`); player builds it only for non-catalog tracks in time-shifted mode (`player.ts:201-211,1997-2004`). Library never sends REQUEST_UPDATE unless `subscribeUpdate()` is called, which the player never calls. `SubscribeOk.largestLocation` is surfaced (`:1110`); player computes `expected = largest - delay_groups` and flags `clampedByRelay = actual > expected` (`player.ts:2043-2048,1180`).
- pr1378 routes the relay's catch-up FETCH_HEADER (request id = PUBLISH id) into the same receiver as live SUBGROUPs (diff `client.ts` +443-482); pr1674 routes fill-fetch streams onto the SUBSCRIBE and counts them toward Stream Count (+737-771).
- Datagram path exists but player never enables it (`player.ts:316-319` passes no options); `dataStreamTimeoutMs`/`controlStreamTimeoutMs` undefined so no idle timeouts; no EarlyDiscardPolicy set. None of these can fire in the experiments.

## Findings

**[Major] Objects for an unrouted alias are read off the wire and silently discarded** — `client.ts:2360-2387, 2460-2463` (all branches). `RecvStream.new` fully parses the header, then `#ingestLoop` keeps pulling and enqueueing with no backpressure (`data_stream.ts:235,257`). If `subscriptions.get(alias)` is empty for 500 ms (2 s on pr1378/pr1674), a `ProtocolViolationError` is thrown, caught at `:2220` and only logged; the reader is never cancelled, so the stream drains to completion and the bytes are counted nowhere. This happens on harness for every old-track stream the relay opens _after_ the switch lands (native callback deletes the old alias at `:1338`), on pr1378 for old-alias streams after PUBLISH_DONE completion (`:2454`), on pr1674 after `#retireSwitchedRequest`. Consequence: player `DROP_STALE` bytes (`player.ts:798-806`) under-count link usage, and the probe's `v + p` (`player.ts:1688-1692`) excludes these bytes while they share the link. Fix: on route-miss, emit an event with header + byte count and `reader.cancel(streamResetReason(Cancelled))` (STOP_SENDING) so the relay stops sending.

**[Major] Native SWITCH refusal deletes the live subscription from `requests`** — `handler/request_error.ts:58-59` with `client.ts:2117-2118,1294` (harness). A REQUEST_ERROR answering SWITCH arrives on the _original_ SUBSCRIBE's stream, so the handler's `requestId` is the original id; it resolves the request and `requests.delete(requestId)` removes the still-active subscription. Player rolls back `videoStruct.requestId` (`player.ts:1846`); the next `switchTrack` passes the alias check (`subscriptionAliasMap` untouched), then `requests.has()==false` → `ProtocolViolationError` → `disconnect()` (`:1294,1352`). Any relay-side SWITCH refusal becomes a session kill one switch later. Fix: in `request_error.ts` only delete when the request's own promise was the pending one, or have `switch()` keep its pending resolver separately from `SubscribeRequest.#promise`.

**[Major] pr1378: alias reuse (relay alias = `relay_track_id`) lets old-receiver completion delete the new route** — `client.ts:2452-2456` (harness code, bites pr1378). On A→B→A the second PUBLISH registers `subscriptions.set(aliasA, receiverA')` (`publish.ts` diff +579). If the first A subscription's last counted stream finishes afterwards, `this.subscriptions.delete(header.trackAlias)` removes A' unconditionally; all later A' streams fall into the silent-discard path and playback freezes with no event. pr1674 guards this (`#releaseTrackAlias`: `if (this.subscriptions.get(trackAlias) !== holder) return`). Fix: same identity guard on harness/pr1378.

**[Major] pr1378: PUBLISH_DONE for a pushed subscription is a no-op** — `handler/publish_done.ts:33-39` (pr1378). Pushed receivers live only in `subscriptions`/`pushedRequestStreams`, not `requests`, so Close-After-Switch on a second switch never closes the old receiver's `ReadableStream`, never removes its alias route, never deletes `pushedRequestStreams`. Trailing objects are enqueued into an abandoned stream (the player aborted its pipe, `player.ts(pr1378):2147-2148`) — unbounded buffering, invisible to DROP_STALE. Fix: in `handlerPublishDone` look up `subscriptionAliasMap.get(openingRequestId)` and apply the same `expectedStreams` close/cleanup.

**[Minor] No backpressure; receive time is stamped after MSE append** — `data_stream.ts:235`, `client.ts:2441`; `player.ts:1060-1063,1121`; `goodput.ts:91`. Both the per-stream parser and the per-subscription `ReadableStream` enqueue unboundedly; `pipeTo` into the MSE `WritableStream` serialises appends, and `GoodputTracker.recordObject` stamps `Date.now()` after `appendBuffer` + `waitForBufferUpdate`. A group's "delivery time" is first-to-last _consume_ time, bounded below by MSE append latency and inflated when a previous group's objects queue ahead; a GOP arriving in one QUIC flush is timed by consumer pace, not arrival pace. Same path on all arms (no between-arm bias) but THROUGHPUT_SAMPLE is goodput-into-MSE, not link throughput. Fix: stamp `performance.now()` at enqueue in `#handleRecvStreams` and carry it on `MoqtObject`.

**[Minor] `onDataReceived` fires twice for the header** — `data_stream.ts:184` and `:200`. Harmless today (unused), would double-count if adopted for timing.

**[Minor] Native switch bookkeeping leaks** — `client.ts:1308,1333-1334,1104-1105`. Old `subscriptionRequestId` never leaves `requests`/`subscriptionAliasMap`; `requestIdMap` re-maps the _old_ id to the _new_ track name. `unsubscribe(newId)` before landing finds no alias (`:1167`) and leaves the route. The player uses `subscriptionAliasMap` as its landing oracle (`player.ts:815,1794`), so this map's semantics matter.

**[Minor] pr1674 hard-mode discards are library-internal** — `request/subscribe.ts(pr1674) +1753-1756`: objects of a superseded request are dropped with `logger.warn`, then the stream is STOP_SENDING'd. Soft-mode drains _are_ delivered with the old `fullTrackName`, which the player then counts as DROP_STALE after landing (`player.ts:790-806`). So DROP_STALE means "library delivered, player refused" on pr1674-soft and harness, but excludes library-level discards on pr1674-hard and pr1378 — the arms are not measured on the same basis.

**[Minor] 500 ms busy-poll per unrouted stream** — `client.ts:2384` (10 ms `setTimeout` loop per stream). Many trailing old-track streams after a switch means many concurrent timers on the main thread at the seam. pr1674's waiter set is the right shape.

## Guarantees the library actually gives the player

1. Within one QUIC stream (one subgroup): objects arrive in wire order, `location` = header group + decoded object id.
2. Across streams: **no ordering**. Streams are served concurrently (`:2215`); groups/subgroups interleave arbitrarily into one `ReadableStream`. On pr1378 catch-up FETCH objects and live SUBGROUP objects interleave on the same stream; on pr1674-soft old-track drain and new-track objects interleave. The player tolerates this only because it drops by track name and keys goodput on group roll-over (`player.ts:1120-1138`), which mis-finalises a sample when groups interleave.
3. Track identity of an object = `aliasFullTrackNameMap[alias]` at enqueue time (harness/pr1378) or the owning request's name (pr1674). Aliases are per _track_, so a same-track re-subscription cannot be distinguished by name.
4. **No receive timestamp**; the only stamps are the player's post-append `Date.now()`.
5. Objects whose route is gone are discarded with a log only, after the stream is fully drained from the wire.
6. The subscription stream closes only when `PUBLISH_DONE.stream_count` is non-zero and equals accepted streams (`:2452`); `stream_count = 0` never closes (falsy check); the probe relies on its own 250 ms idle timer (`player.ts:1637`).
7. SUBSCRIBE_OK `largestLocation` is reported as sent; no clamp logic in the library.

## Branch differences beyond the mechanism (Q7)

- pr1378: route-wait 500 ms → 2000 ms (`DATA_ROUTE_WAIT_TIMEOUT_MS`), 10 ms → 20 ms poll; 6 s client-side switch timeout with tombstones; `unsubscribe()` extended to pushed subscriptions; PUBLISH_DONE on pushed streams is a no-op (finding above). The 2 s route-wait means unrouted streams are drained for up to 2 s longer (more hidden link usage) — a mild bias toward hiding pr1378 trailing bytes.
- pr1674: `forward` becomes optional (omitted → relay default), filter types renamed to *Fill, `FetchType` removed, event-driven alias waiters (2 s), `Subscription` manager with drain timer (2 s), identity-guarded alias release, `completeSubscription` also triggered from PUBLISH_DONE, fill-fetch streams counted toward Stream Count. The alias-release guard and PUBLISH_DONE-triggered completion fix two of the harness/pr1378 bugs above, so pr1674 is the only arm that cleans up correctly on A→B→A; this favours pr1674 in long runs with returns to a previous rendition.
- Neither branch changes the data-stream parser, enqueue path or timing, so per-object delivery semantics are identical across arms.

## Simplification opportunities

- Port `#claimTrackAlias`/`#releaseTrackAlias` (pr1674) to all branches, replacing `pendingStateUpdates` (`:1325-1340`) and the poll loop; removes the alias-collision bug class.
- Add one `onStreamDiscarded(header, bytes, reason)` hook in `#handleRecvStreams` and emit `DROP_STALE{reason:'unrouted'}` from the player, so all arms count discarded bytes on the same basis.
- Stamp `recvAt = performance.now()` on `MoqtObject` at `:2430/2346`; goodput can then measure arrival spacing independent of MSE.
- `handlerRequestError` must not delete by stream id for a SWITCH on a SUBSCRIBE stream; cheapest fix is a separate pending-switch resolver rather than reusing `SubscribeRequest.#promise`.
- The joining-fetch `FetchHeader` path (`:2315-2325`) is dead code for the player on all branches (already removed on pr1674).
